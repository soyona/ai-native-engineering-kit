# AI Native 工程规范

在 Codex 中打开新项目文件夹，发送这一句话：

```text
请读取 https://github.com/soyona/ai-native-engineering-kit 的 README，按照其中的初始化指南，在当前目录初始化我的新项目。
```

完成后，打开**自己项目根目录的 `README.md`**，就能看到「已经创建或复用」和「按需启用」两部分。空目录默认建立七类资料目录和 `scripts/`；已明确工程形态时，同一句提示词还会建立相应的源码、测试与配置目录。无需先选技术栈或安装工具。

## 初始化指南（给 Codex）

1. **先选结构。** 唯一写入位置是用户打开的目标项目。按下文三张表列出：基础目录、当前适用的工程目录、未启用项。以用户明确说明、已有布局和必要的构建清单为依据；不遍读业务资料、密钥或个人配置。README 的“按需启用”列表不是启用证据。技术栈不明就完成基础层，不阻塞初始化。无法取得规范来源时停止。
2. **写入前预检。** 检查所有拟创建/复用路径、父目录与根 README。已有普通目录复用；遇到文件占用目录、路径越出项目、符号链接/目录联接等重解析点、README 类型错误或需要确认的写入冲突，先停止并报告，不留下半套目录。模块名只使用确认的项目内相对路径。
3. **建立目录，生成项目自己的指南。** 实际建齐已选目录。根 README 用「已经创建或复用」说明实际路径、何时用、放什么；用「按需启用」列出此项目尚未建立的相关目录及触发条件，不把它们计入完成项。不要把规范仓库的整份 README 复制给用户。只有根 README 是默认生成的文件；不生成业务代码、构建文件、占位文件、CI 工作流、部署配置或凭据，不提交、不上传。
4. **保留已有内容。** 按路径和语义去重；旧版七项目录指南有效，只补 `scripts/`、适用的工程路径和未启用说明。已由本指南生成的状态若有变化（例如后来选定 Maven），将对应条目从待启用转到已启用，不留两种状态。已有用户正文不移动、不覆盖；无法安全维护原说明或出现矛盾时先确认。所有需改写已有 README 的情况，均在创建目录前确认编码、BOM、换行风格及硬链接数为 1；不能可靠判断或硬链接数大于 1 时停止。Windows 可用 `fsutil hardlink list` 检查。同样的输入再次执行应无任何差异。
5. **检查并报告。** 将已选清单与磁盘逐项核对，检查指南中的实际路径确实存在、未启用路径没有被误建。告诉用户本次采用的结构、新建/复用项和指南位置。中途失败说明已发生的变更，不删除用户文件。空目录可能不会随 Git 提交保留，新检出项目可用同一句提示词补齐。

## 一、基础目录：每个项目都建

以下路径都相对于用户项目的根目录。已有原件可以保留在原位置，无需为符合这张表而搬动。

| 目录 | 什么时候用 | 典型内容 |
| --- | --- | --- |
| `docs/inputs/` | 收到尚未整理的资料时 | 访谈原稿、客户来稿、调研记录。 |
| `docs/requirements/` | 整理项目要解决的问题、功能范围和验收条件时 | 产品需求文档（PRD）、功能规格、验收条件。 |
| `docs/design/product/` | 设计用户如何完成任务时 | 用户流程、页面原型、交互与异常状态说明。 |
| `docs/design/technical/` | 确定功能如何实现时 | 架构设计、模块职责、接口契约、数据模型。 |
| `docs/development/` | 安排或记录开发工作时 | 实施计划、任务拆解、变更记录；不放业务源码。 |
| `docs/verification/` | 检查功能是否满足需求时 | 测试用例、实际测试结果、业务验收记录。 |
| `docs/delivery/` | 向使用方交付版本时 | 版本说明、使用手册、部署与交接记录。 |
| `scripts/` | 维护项目或重复执行工程操作时 | 环境准备、校验、构建或数据处理脚本；不放产品源码。 |

## 二、工程目录：按项目形态创建

| 判定依据 | 实际创建或复用 | 不应创建 |
| --- | --- | --- |
| 空项目，形态未定 | 仅建基础目录；指南说明源码、测试和配置等待选型 | `src/`、`tests/`、`config/`、`apps/` 等技术目录 |
| 已明确为单应用，无框架专属布局 | `src/` 放产品源码，`tests/` 放可执行测试与测试样本，`config/` 放可共享的配置示例 | 已有等价路径时，不另建同用途目录；不写入密钥 |
| 已确定是 Java Maven 单应用（例如根 `pom.xml` 指明普通 Java 应用） | 默认用 `src/main/java/` 放业务源码、`src/main/resources/` 放应用资源和配置、`src/test/java/` 放测试。已明确的自定义路径优先 | 不另建根 `tests/`、`config/`；聚合 POM 按实际子模块处理 |
| 已确认多应用同仓且应用名称已知 | 新仓用 `apps/<应用名>/`，分别应用本表的工程布局。已有 `frontend/`、`backend/` 或清单声明的模块，保留名称并按实际子项目处理 | 不创建字面量占位名，不平行建 `apps/` 或根 `src/`；有真实共享代码才建 `packages/` |

已有材料不搬动。技术信息不足时可以记录“待选型”；模块内的技术栈相互独立，不因后端使用 Maven 就把前端也生成为 Maven 项目。

## 三、扩展目录：确有用途再建

明确要求、已有等价目录，或项目中已确认的对应实践才启用。缺少证据时只在指南的“按需启用”中说明。框架已有专用路径时优先复用。例如迁移已放在应用资源内，不再创建第二个 `db/migrations/`。

| 可选路径 | 启用条件与用途 |
| --- | --- |
| `docs/requirements/features/` | 按功能独立维护规格时，放场景、边界和验收条件。 |
| `docs/design/product/prototypes/` | 有原型或设计稿时，放原型源文件或外部设计链接。 |
| `docs/design/technical/decisions/` | 需要记录重要取舍时，放技术决策及其依据。 |
| `contracts/` | 多端共用机器可读契约时，放 OpenAPI、事件或文件格式定义；设计理由仍放技术设计目录。 |
| `db/migrations/`、`db/seeds/` | 分别在需要数据库迁移、开发/测试种子数据时启用；不放生产数据。 |
| `deploy/`、`infra/` | 分别用于已确定的部署配置和基础设施代码；操作手册仍放 `docs/delivery/`。 |
| `.github/workflows/` | 已选用 GitHub Actions 时启用；仅托管于 GitHub 不代表已选 CI。 |
| `.agents/skills/` | 有项目专属的可复用 Codex 流程时启用。 |

`AGENTS.md` 和 `.gitignore` 是可选**文件**：前者承载项目专属协作规则，后者在使用 Git 时约定排除项。保留已有文件；不因目录初始化自动生成它们。测试代码放可执行测试目录，测试结果与业务验收结论放 `docs/verification/`。
