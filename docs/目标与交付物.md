# AI Native 工程规范：目标与交付物

状态：已冻结（v1.7）｜日期：2026-11-25

## 1. 目标

**用户在新项目目录中向 Codex 发送一句提示词，即可建立从需求到交付的资料目录和适合该工程的工作目录。打开项目根目录的 `README.md`，用户能区分哪些已创建或复用、哪些待启用，并知道每个目录何时用、放什么。**

首次使用提示词（冻结原文）：

> 请读取 https://github.com/soyona/ai-native-engineering-kit 的 README，按照其中的初始化指南，在当前目录初始化我的新项目。

规范仓库的 README 提供初始化指南；用户项目根目录的 README 提供目录使用指南。空目录即可初始化，无需先提供需求或选定技术栈；已有资料时，保留原文件与位置，不移动、不覆盖。

## 2. 初始化交付物

1. **实际创建的项目目录。** 默认建立七类资料目录和 `scripts/`；技术栈、应用边界或工程用途明确时，再建立相应目录。已有等价路径优先复用，不生成平行目录。目录可以为空。
2. **一份目录使用指南。** 根 README 将“已创建或复用”和“按需启用”分开，逐项说明实际路径、用途和典型内容，保留既有说明并按语义补缺。再次初始化应能从基础结构扩展到已确定的工程形态。

## 3. 目录及用途

以下路径相对于用户项目根目录。

| 目录 | 什么时候用 | 典型内容 |
| --- | --- | --- |
| `docs/inputs/` | 收到尚未整理的原始资料时 | 访谈原稿、客户来稿、调研材料；已有原件可以留在原处。 |
| `docs/requirements/` | 说明要解决什么问题、功能怎样才算满足需求时 | 项目范围、PRD、功能规格、验收条件。 |
| `docs/design/product/` | 设计用户如何完成任务时 | 用户流程、页面原型、交互与异常状态说明。 |
| `docs/design/technical/` | 决定功能如何实现时 | 架构设计、模块职责、接口契约、数据模型。 |
| `docs/development/` | 安排和记录开发工作时 | 实施计划、任务拆解、关联变更记录；不存放业务源码。 |
| `docs/verification/` | 核对需求是否满足时 | 测试用例、测试结果、业务验收记录。 |
| `docs/delivery/` | 向使用方交付版本时 | 版本说明、使用手册、部署与交接记录。 |
| `scripts/` | 维护项目、执行工程任务时 | 环境准备、校验、构建或数据处理脚本。 |

**工程目录按形态启用：** 普通单应用使用 `src/`、`tests/`、`config/`；已确定框架时优先使用其原生布局。多应用按确认的边界分目录；已有 `frontend/`、`backend/` 等布局直接复用。功能规格、原型、技术决策、接口契约、数据库、部署、基础设施、CI 和 skills 的具体归属与启用条件见[发布规范中的目录表](../README.md)。资料与机器执行的文件分开：测试结果放验证文档，测试代码放所属应用的测试目录。

## 4. 完成标准与边界

- **目录存在：** 未定栈空项目只建立七类资料目录和 `scripts/`；已确定的单应用或多应用还应建立适用的工程目录，不得凭空启用其他技术目录。
- **说明可用：** 根 README 区分已启用和待启用目录。用户能据此放对访谈、需求、源码、测试和交付材料，且不会把未生成的目录误认为已经存在。
- **原件保留：** 在已有资料的项目中初始化，原件不被移动或覆盖；重复初始化不重复添加指南。

技术选型、业务代码、构建文件、可执行 CI 工作流、各阶段文档的编写及部署均不属于目录初始化交付物。创建目录不等于工程可运行；没有业务资料也能完成初始化。

以上目录只生成在用户项目中，不在规范仓库自身创建示例空目录。
